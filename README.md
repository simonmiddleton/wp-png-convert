# wp-convert-images-to-jpg

A Python script that converts PNG, BMP, and TIFF images in a WordPress uploads directory to JPEG, then updates the WordPress database to match.

Designed for bulk media library migrations where PNG is the dominant format and storage space or delivery performance matters. Dry-run by default — it will tell you exactly what it plans to do before touching anything.

## Introduction

This script was created because I had a website that had around 10000 images that had been uploaded as PNG files (plus all the scaled variants) which were consuming more disk space than needed. None of the plugins I looked at would do what I wanted, which was to just reliably convert a large number of images in the background.

It is almost entirely generated by Claude Sonnet 4.6 over the course of a morning, with a few iterations to optimise the original script (from 12 hours to 10 minutes on a MacBook Pro M5) and make it robust.

It's not terriibly sophisticated but it does what I needed so it's here in case it helps you too.

## Features

- Converts PNG, BMP, TIF, and TIFF files to JPEG, including all WordPress-generated size variants (`-150x150`, `-scaled`, etc.)
- Backs up the original (unscaled) master image before conversion, preserving the directory structure
- Transparently handles images with alpha channels by compositing them onto a white background
- Recovers from truncated variant files by regenerating the size directly from the master
- Updates the WordPress database:
  - Attachment post `guid` and `post_mime_type`
  - `_wp_attached_file` postmeta
  - `_wp_attachment_metadata` (PHP-serialised, with correct `s:N:` byte-length fixup)
  - `post_content` across all live posts in a single batched pass, excluding revisions
- Reads database credentials automatically from `wp-config.php`
- Press any key during a run to stop cleanly after the current image
- Reports disk space saved (originals vs JPEGs, backups not counted)

## Requirements

- Python 3.9+
- [`uv`](https://docs.astral.sh/uv/) (recommended) — handles dependencies automatically via the inline script metadata
- MySQL/MariaDB access to the WordPress database
- Linux or macOS (uses `termios` for the keypress-to-stop feature)

Dependencies (installed automatically by `uv`): `Pillow >= 10`, `pymysql >= 1.1`, `rich >= 13`.

## Usage

```bash
# Dry run — scan and report what would change, no files or DB touched
uv run convert_images_to_jpg.py

# Apply changes
uv run convert_images_to_jpg.py --execute
```

Run the dry run first. It prints every file it would convert and every backup it would create, and reports the total size of originals so you can estimate savings before committing.

### Options

| Flag | Default | Description |
|------|---------|-------------|
| `--execute` | off | Apply conversions and DB updates (dry run if omitted) |
| `--wp-root DIR` | `.` | WordPress root directory |
| `--uploads-dir DIR` | `<wp-root>/wp-content/uploads` | Uploads directory to scan |
| `--backup-dir DIR` | `<wp-root>/image-backups` | Where to copy original masters before conversion |
| `--quality N` | `90` | JPEG quality, 1–95 |

### Stopping mid-run

Press any key while the script is running to stop cleanly after the current image group finishes. The summary will report how many groups were processed. All database changes committed up to that point are preserved.

## What gets updated in the database

For each converted image the script:

1. Looks up the attachment's `post_id` via an exact match on `_wp_attached_file` (indexed, no table scan).
2. Updates `wp_posts.guid` and `post_mime_type` by primary key.
3. Updates `_wp_attached_file` in `wp_postmeta` by `post_id`.
4. Deserialises `_wp_attachment_metadata`, replaces all filenames and MIME type strings with correct PHP `s:N:` length prefixes, and writes it back.
5. After every 1000 groups (and once at the end), scans `post_content` in a single pass across all live posts — excluding revisions and attachments — and applies all accumulated filename replacements in Python before writing back only the rows that actually changed.

## Transparency and alpha channels

JPEG does not support transparency. Any image with an alpha channel (RGBA, LA, or palette mode with transparency) is composited onto a plain white background before saving. If you need a different background colour, edit the `Image.new('RGB', img.size, (255, 255, 255))` calls in `convert_to_jpg` and `regenerate_variant_from_master`.

## Truncated variant files

If a size variant (e.g. `-300x250.png`) cannot be opened because it is truncated or corrupt, the script automatically regenerates it by resizing the master image to the correct dimensions (read from the filename) using high-quality Lanczos resampling, then deletes the truncated original. The master itself is never auto-regenerated — truncated masters are reported as errors.

## Backups

Only the master (original, unscaled) image is backed up. Size variants are not backed up because they can be regenerated from the master at any time using WordPress's **Regenerate Thumbnails** plugin or WP-CLI (`wp media regenerate`).

The backup directory mirrors the uploads directory structure:

```
image-backups/
  2023/
    04/
      my-photo.png      ← original master, before conversion
  2024/
    01/
      another.png
```

Backups are not counted when reporting disk space savings.

## Running without uv

If you prefer to manage dependencies yourself:

```bash
pip install "Pillow>=10" "pymysql>=1.1" "rich>=13"
python convert_images_to_jpg.py --execute
```

## Database credentials

Credentials are read from `wp-config.php` in the WordPress root. If a `local/wp-config.php` file exists alongside it (a common local-development pattern), values defined there take priority.

The script reads `DB_HOST`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`, and `$table_prefix`. No configuration file or environment variables are needed.

## Caveats

- **Test on a staging copy first.** This script modifies both files and the database. Run with `--execute` only after reviewing the dry-run output and confirming your backups are in place.
- **No CDN / object storage support.** The script works on local filesystem uploads only. If your media is served from S3, a CDN, or similar, the file operations will need adapting.
- **Reusable blocks (`wp_block`) and classic shortcodes** that embed images by filename are updated via the `post_content` pass. Images referenced only by attachment ID (standard Gutenberg blocks) need no `post_content` update and are handled entirely through the attachment metadata.
- **Revisions are intentionally skipped** in the `post_content` update. WordPress revisions are historical snapshots that are never served to users; updating them is wasted work. If a revision is ever restored, WordPress will show a diff before applying it.
